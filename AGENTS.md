# 🤖 AGENTS.md — Архитектура, философия и руководство для AI-агентов

> Этот документ предназначен для AI-агентов (Antigravity, Claude, Copilot, Cursor и др.) и разработчиков, работающих с кодовой базой **`devtool-script`** (`dev`).  
> Он описывает архитектуру системы, философию проекта, принципы реализации и правила добавления новых сценариев.

---

## 🎯 1. Обзор проекта

**`devtool-script`** — это легковесный, модульный и расширяемый CLI-лаунчер (`dev`) для автоматизации сложных задач разработки, DevOps, Git и обслуживания серверного окружения.

Вместо раздутого и непереносимого `.bashrc` с сотнями хрупких `alias`, проект предоставляет:
- Единую точку входа: бинарник `dev`.
- Декларативные скрипты с метаданными в комментариях.
- Интерактивный поиск с live-preview (`fzf` или встроенное меню).
- Трехуровневое хранилище (проектное, пользовательское, базовое).
- Автоустановку и самообновление через Git в одну строку `curl | bash`.

## 🧭 2. Философия проекта

При разработке и модификации утилит в этом репозитории **всегда** соблюдаются следующие фундаментальные принципы:

### 2.1. Никаких тривиальных однострочников (Anti-Triviality)
В репозитории **запрещено** создавать скрипты, являющиеся простой оберткой над очевидной командой (например: `git log`, `docker ps`, `php artisan tinker`, `php artisan migrate`). Разработчик и так помнит эти команды наизусть.

**Сюда попадают ТОЛЬКО:**
- Команды с длинными, сложно запоминаемыми пайплайнами (`rev-list + cat-file + awk + sort`, `openssl s_client | openssl x509`, `grep ': gone]' | xargs branch -D`).
- Многосоставные сценарии из 5–10 шагов (деплой, полный сброс Laravel, глубокая зачистка Docker с BuildKit).
- Нестандартные сценарии со сложной логикой (привязка «сырых» файлов с хостинга к Git без перезаписи, запуск Composer в Docker без установленного PHP).

### 2.2. Нулевые внешние runtime-зависимости (Zero Dependencies Core)
- Ядро лаунчера и все базовые скрипты написаны на **чистом Bash 4+**.
- Никаких обязательных Python, Node.js, Ruby или скомпилированных бинарников для работы самого лаунчера.
- Утилита `fzf` является **опциональной**: если она есть — используется интерактивный fuzzy-поиск с превью; если ее нет — лаунчер бесшовно переключается на встроенное текстовое меню.

### 2.3. Декларативные метаданные (Self-Describing Scripts)
Скрипт сам описывает себя в заголовках. Лаунчер никогда не требует хардкода списка команд в исходном коде `bin/dev`. Достаточно положить `.sh` файл в папку категории.

### 2.4. Защита от случайных разрушений (Safety First)
Любая операция, способная привести к потере незакоммиченного кода, удалению веток, сбросу баз данных или остановке сервисов, **обязана** иметь флаг `# @dangerous true`. Лаунчер перехватывает такие скрипты и запрашивает подтверждение `[y/N]`, если не передан флаг `--force` или `-y`.

### 2.5. Git-центричность (Git as Distribution Engine)
- Репозиторий самодостаточен.
- Установка выполняется клонированием или через `curl -fsSL ... | bash`.
- Обновление выполняется через `dev update` (`git pull --ff-only`).

| Компонент | Технология | Описание |

## 🏛 4. Как это реализовано (Архитектура)

### 4.1. Структура каталогов

```text
devtool-script/
├── bin/
│   └── dev                  # Единая точка входа и диспетчер команд
├── lib/
│   └── utils.sh             # Вспомогательные функции (парсинг, UI, поиск)
├── scripts/                 # Базовые сценарии репозитория
│   ├── git/                 # Сложные операции Git
│   ├── docker/              # Комплексные операции с Docker/Compose
│   ├── laravel/             # Сценарии Laravel и Docker Sail
│   ├── server/              # Системные и сетевые утилиты DevOps
│   └── dev/                 # Сервисные скрипты самого лаунчера
├── install.sh               # Автоустановщик (curl | bash и локальный)
├── uninstall.sh             # Скрипт очистки симлинков и каталога
├── AGENTS.md                # Этот документ
└── README.md                # Пользовательская документация
```

### 4.2. Трехуровневое хранилище (Multi-Tier Discovery)

При вызове любой команды лаунчер ищет скрипт в следующих местах по приоритету (сверху вниз):

1. **Проектный уровень**: `$PWD/.dev/scripts/` или `$PWD/.dev/`
   - Позволяет конкретному репозиторию проекта переопределять или расширять команды `dev` (например, проектный `./.dev/test/e2e.sh`).
2. **Пользовательский уровень**: `$DEV_EXTRA_SCRIPTS` или `~/.config/devtool/scripts/`
   - Для персональных скриптов разработчика, которые не должны попадать в публичный репозиторий.
3. **Базовый уровень**: `$DEV_ROOT_DIR/scripts/`
   - Встроенная библиотека сценариев из этого репозитория.

### 4.3. Парсер метаданных (`get_metadata`)

Каждый скрипт содержит в начале специальный блок комментариев:

```bash
#!/usr/bin/env bash
# @name Человекочитаемое название
# @description Подробное описание того, что делает скрипт
# @usage dev category command [параметры]
# @dangerous true|false

set -e
```

Функция `get_metadata "$file" "$key" "$default"` в [`lib/utils.sh`](file:///home/gregorybiter/dev/devtool-script/lib/utils.sh) парсит регулярным выражением:
`^#[[:space:]]*@${key}[:=]?[[:space:]]+`
Это позволяет извлекать информацию без выполнения самого скрипта.

### 4.4. Маршрутизация аргументов в `bin/dev`

Лаунчер поддерживает несколько стилей вызова для максимальной гибкости:

```bash
dev git purge-branches    # Стандартный формат: dev <категория> <команда>
dev git-purge-branches    # Формат алиаса: dev <категория>-<команда>
dev git:purge-branches    # Формат неймспейса: dev <категория>:<команда>
dev purge-branches        # Автопоиск: dev <уникальное_имя>
dev git                   # Меню с фильтрацией по категории git
dev                       # Полное интерактивное меню
```

Флаги лаунчера (`--force`, `-y`, `--help`, `-h`, `--version`) обрабатываются до передачи управления скрипту. Все последующие позиционные аргументы передаются в скрипт через `exec bash "$script" "$@"`.

### 4.5. Механизм защиты опасных операций

Перед выполнением любого скрипта вызывается `confirm_if_dangerous`:
1. Если `@dangerous != true` $\to$ запускается сразу.
2. Если установлена переменная `DEV_FORCE=1` или передан флаг `--force` / `-y` $\to$ запускается без вопросов.
3. В противном случае в терминал выводится желто-красный блок с предупреждением, описанием команды, целевым файлом и запросом подтверждения `[y/N]`. При отказе скрипт немедленно прерывается с кодом `1`.

## 📋 5. Каталог базовых сложных сценариев

### Категория `git`:
- **`sync-hosting.sh`** (`dev git sync-hosting [url] [branch]`):  
  Привязка локальной папки, скачанной с хостинга, к Git-репозиторию без перезаписи файлов. Выполняет `symbolic-ref HEAD` + `reset origin/<branch>`, анализирует дельту (измененные, добавленные и удаленные на сервере файлы) и создает безопасную ветку `hosting-sync-...`.
- **`purge-branches.sh`** (`dev git purge-branches [--force]`):  
  Удаление локальных веток, которые уже слиты или помечены сервером как `[gone]` после `git fetch -p`, с защитой веток `main`, `master`, `develop`, `staging`.
- **`find-large.sh`** (`dev git find-large [N]`):  
  Глубокое сканирование всех pack-файлов и деревьев репозитория через `git rev-list --objects --all` и `git cat-file --batch-check` для поиска самых тяжелых блобов в истории с форматированием в MB/KB.
- **`squash.sh`** (`dev git squash [N]`):  
  Мягкое объединение последних $N$ коммитов в один с переносом изменений в staging (`git reset --soft HEAD~N`).
- **`undo.sh`** (`dev git undo`):  
  Интерактивный откат последнего коммита с выбором: `--soft` (в staging), `--mixed` (на диск), `--hard` (удалить) или просмотр точек восстановления через `git reflog`.

### Категория `docker`:
- **`nuke.sh`** (`dev docker nuke [--volumes]`):  
  Комплексная глубокая зачистка: остановка всех контейнеров $\to$ удаление контейнеров $\to$ `system prune -a` $\to$ очистка кэша сборщика **BuildKit** (`builder prune -a`) $\to$ очистка томов $\to$ вывод освобожденного дискового пространства.
- **`db-dump.sh`** (`dev docker db-dump [container]`):  
  Автоопределение типа базы данных (MySQL / MariaDB / PostgreSQL), чтение реквизитов из env-переменных контейнера и потоковая выгрузка дампа через `docker exec` сразу в сжатый `.sql.gz` на хосте.
- **`rebuild.sh`** (`dev docker rebuild [service]`):  
  Пересборка Docker Compose: `down --remove-orphans`, сборка `--no-cache`, запуск в фоне и валидация статусов контейнеров.

### Категория `laravel`:
- **`sail-setup.sh`** (`dev laravel sail-setup`):  
  Полная инициализация проекта с нуля через Sail: автогенерация `.env` $\to$ установка Composer через временный Docker-контейнер без PHP на хосте $\to$ запуск `sail up -d` $\to$ генерация `APP_KEY` $\to$ `sail npm install && sail npm run build` $\to$ ожидание БД и выполнение миграций.
- **`sail-install.sh`** (`dev laravel sail-install`):  
  Изолированная установка Composer-пакетов через Docker-образ `laravelsail/phpXX-composer` под текущим пользователем (`-u $(id -u):$(id -g)`).
- **`sail-npm.sh`** (`dev laravel sail-npm [args...]`):  
  Проксирование любых команд NPM (`install`, `build`, `run dev`) внутрь рабочего окружения Sail с контролем статуса контейнеров.
- **`reset.sh`** (`dev laravel reset`):  
  Глубокий 8-шаговый hard-reset: `artisan down` $\to$ очистка кэшей и `bootstrap/cache/*.php` $\to$ `composer dump-autoload -o` $\to$ `migrate:fresh --seed` $\to$ `storage:link` $\to$ `queue:restart` $\to$ права 775 $\to$ `artisan up`.

### Категория `server`:
- **`kill-port.sh`** (`dev server kill-port <port> [-9]`):  
  Поиск процесса, занявшего сетевой порт (через `lsof`, `fuser` или `ss`), сбор информации о PID, пользователе и RAM, и отправка сигналов завершения.
- **`disk-usage.sh`** (`dev server disk-usage [path] [N]`):  
  Поиск $N$ самых крупных каталогов и файлов через `du -ahx` с защитой от сканирования псевдо-ФС (`/proc`, `/sys`, `/dev`).
- **`ssl-check.sh`** (`dev server ssl-check <domain> [port]`):  
  Проверка SSL-сертификата удаленного хоста через `openssl s_client`: точный расчет оставшихся дней, дата истечения, эмитент и SAN.
- **`permissions.sh`** (`dev server permissions [path]`):  
  Расстановка безопасных стандартных прав: 755 для директорий, 644 для файлов, 775 для `storage` и `bootstrap/cache`.
- **`deploy.sh`** (`dev server deploy [branch]`):  
  Пошаговый цикл продакшн-деплоя: Git pull $\to$ Composer no-dev $\to$ NPM build $\to$ миграции $\to$ оптимизация кэша $\to$ перезапуск воркеров.

### Категория `dev`:
- **`update.sh`** (`dev update`): Самообновление из Git с показом лога коммитов и актуализацией прав на новые скрипты.
- **`doctor.sh`** (`dev doctor`): Диагностика утилит (Bash, Git, Docker, PHP, Composer, Node, NPM, fzf).
- **`create.sh`** (`dev dev create <category> <name>`): Шаблонизатор для быстрого создания новых сценариев.

## 🛠 6. Руководство для AI-агентов: Как добавлять новые скрипты

Когда пользователь просит добавить новый скрипт или автоматизировать сложный процесс, следуйте этому алгоритму:

### Шаг 1: Проверка на нетривиальность
Задайте себе вопрос: *«Это однострочник, который легко запомнить, или сложная цепочка команд со флагами и логикой?»*  
Если это тривиальная команда (например, `git status` или `npm start`), **не создавайте** скрипт.

### Шаг 2: Создание файла в правильной категории
Поместите скрипт в `scripts/<category>/<command_name>.sh`.  
Имя файла должно быть в `kebab-case` с расширением `.sh`.

### Шаг 3: Обязательный заголовок метаданных
Каждый новый файл обязан начинаться с метаданных:

```bash
#!/usr/bin/env bash
# @name Краткое и понятное название
# @description Четкое описание операции (показывается в dev list и превью)
# @usage dev category command_name [параметры]
# @dangerous true # или false

set -e

# Логика скрипта...
```

### Шаг 4: Надежность и безопасность исполнения
- Всегда используйте `set -e` для немедленной остановки при ошибках.
- Проверяйте наличие утилит перед вызовом (`command -v docker >/dev/null 2>&1`).
- Если операция удаляет файлы, ветки или данные, обязательно ставьте `# @dangerous true`.
- Не хардкодите абсолютные пути хоста; используйте относительные пути проекта или переменные `$PWD`.

### Шаг 5: Права на исполнение и регистрация
Выполните:
```bash
chmod +x scripts/<category>/<command_name>.sh
```
Обновите таблицу в [`README.md`](file:///home/gregorybiter/dev/devtool-script/README.md) и закоммитьте изменения в Git.
Лаунчер обнаружит команду автоматически.
